## Bug found: real signals never actually fire
> **FIXED 2026-07-13** — see [session-2026-07-13.md](./session-2026-07-13.md).
> The config frame must be the raw config object with **no `type` field**.

Root cause identified, **not yet fixed**.

The client sends this over the WS after `session.ready`
([interhuman.ts:41-46](../web/src/analyzer/interhuman.ts:41)):

```json
{
  "type": "session.config",
  "analysis_groups": ["audio"],
  "realtime_feedback_frequency": "high",
  "realtime_feedback_instructions": "..."
}
```

The server rejects this immediately with:

```
error ih6001: Invalid session config message: type: Extra inputs are not
permitted. Text frames on this endpoint must be a JSON object matching the
documented session-config schema.
```

...and closes the socket with code `1008`. This happens on **every** real
session, before any audio is ever analyzed — which is why the signal rail
showed "Nothing active" the whole time. It wasn't calm/quiet audio, it was
this handshake bug silently killing the session right after connect.

Confirmed with a standalone probe script (mint token → open WS → send the
exact same config the app sends → push a real synthetic pitch clip
generated via macOS `say` + `ffmpeg` to webm/opus) — same `ih6001` error,
same immediate close, before the audio blob could even be analyzed.
